Wren: a home-made Claude Duet

Anthropic's Claude Duet is a background agent that checks in each morning, does long jobs on its own and asks before it sends or pays. It's waitlist-only for now. We had already built most of the same thing ourselves, out of Claude Code, a server and a handful of open tools. We call it Wren. This is what it's made of, how it compares, and what it taught us.

How it fits together

  • You ask from anywhere. Telegram, the Claude app, the desktop app or ChatGPT.
  • Opus plans and checks. It runs in Claude Code on our own server.
  • Cheaper models do the work. Codex builds, Haiku reads, other agents help over a shared bus.
  • Files keep the state. Checkpoints, notes and lessons live on disk, not in a chat.
  • You approve what leaves. Orders always need a human; a phone gate covers other actions.

How it grew

  • June 2026. Session tooling (crss) lets Claude Code run for days on a server and be reached from a phone.
  • August. A shared message bus lets Claude, Codex, ChatGPT and other agents hand each other work.
  • October. DispatchBench picks the cheapest model for each job, and the orchestrator gets a name, a persona and a memory: Wren.
  • 26 October. A 07:00 Telegram brief, and a phone approve/deny gate, tested live both ways.

How you talk to it

From anywhere. Telegram (typed or voice notes), the Claude app's Remote Control and voice chat, the desktop app, or ChatGPT, which reaches the server through a connector. Every door opens onto the same server and the same memory, so you can run several Wren threads at once. How it fits: this is the front door; everything else on this page sits behind it.

What it's made of

How it fits: these are the parts behind the front door, from the box up.

  • The server: a dedicated server, on 24/7, with root access.
    • Intel i7-8700: 6 cores, 12 threads.
    • 62 GB RAM.
    • 2.8 TB NVMe: three 1 TB drives, striped (RAID0).
    • Ubuntu 24.04, about 35 scheduled jobs (25 timers, 10 cron).
  • Claude Code on a server, signed in to a Max plan. Opus does the planning and checking.
  • crss: starts, messages, hands off and repairs long-running sessions. Every agent on the box runs on it.
  • token-reduce and QMD: read only the slice of a repo or notes folder a task needs. QMD is a local search engine over our markdown.
  • DispatchBench and the delegate skills: each pass goes to the cheapest model that passes it.
    • Opus plans the work and checks it.
    • Codex builds and gives the final review.
    • Haiku does cheap reads and sweeps.
    • Devin takes browser and sandbox jobs.
    • If Codex is out: Haiku takes small builds, and Grok reviews.
    • Fable gave second opinions until we paused it on 28 October.
    DispatchBench measures which model passes each kind of job. New models plug in through the same skills.
  • A soul: a short persona file every session loads. A cheap reviewer can save one lesson before each context reset.
  • Shared memory: plain files on disk, searched by QMD. Details in Memory, honestly.
  • The bus: a small mailbox database where agents post tasks and replies to each other, including Hermes and OpenClaw.
  • Phone bridges: the Hermes gateway and takopi for Telegram; Claude Remote Control for the app.
  • ChatGPT's apps, through Codex: connectors for brokers, market data, GitHub and site hosting.
  • Market data on the server: price feeds (Databento, Yahoo Finance), economic data (FRED), filings (SEC EDGAR) and web search.
  • Daily jobs: scheduled tasks that raise alerts, a daily brief job, and the approval gate.

Memory, honestly

How it fits: memory is how a fresh session picks up where the last one stopped. Here's what we actually run, and how each part can fail.

LayerWhat it doesHow it fails
Boot cardWhatA persona file under 1 KB loads every session. The rest loads only when a task needs it.FailsIf a rule isn't on the card, a small model may never see it.
Curated notesWhatPlain markdown files per agent, in private and public folders. A check script screens them before indexing.FailsOne local git repo with no remote, so it is not a backup.
CheckpointsWhatEach long job keeps one short checkpoint file, plus git commits and receipts. That file is the record, not the chat.FailsA job that skips its checkpoint loses state on reset.
Lesson hookWhatBefore a context reset, Haiku may save one lesson. In its first week it saved seven.FailsMost runs skip on purpose; it is a trickle, not a teacher.
SearchWhatQMD indexes our local files and notes, and refreshes every six hours. token-reduce reads only the slice a task needs.FailsThe index lags; new files wait hours before search finds them.
TranscriptsWhatEvery session's raw log stays on disk. They are never indexed.FailsUseful for forensics, too noisy to search.
BackupsWhatLocal snapshots before risky changes. Code is pushed to GitHub.FailsThe disks are striped, so one dead drive loses the box. Snapshots sit on the same disks. Notes and transcripts have no off-box copy yet.

We also run gbrain, a knowledge-base server. It has been unreliable for us: its health check fails, a sync has aborted, and it needs a repair timer. Nothing depends on it.

If you copy this: add an off-box backup before anything else.

What others do

  • OpenClaw "dreaming": a nightly job rewrites the memory file. If the rewrite drops over a quarter of old entries, it falls back to append-only. It backs up first. We want that guard; we skip the nightly model calls.
  • Hermes: pluggable memory providers, and a curator that retires unused skills. We borrowed the lesson-before-reset idea instead.
  • ChatGPT: saved memories plus references to past chats. Convenient, but it lives in your OpenAI account, not in files you can diff.
  • Papers: MemGPT pages memory in and out like an operating system. Reflexion writes lessons after failures. Our boot card and lesson hook are small versions of both.

What we learned

  • Expensive head, cheap hands. The strong model plans and checks; cheaper models do the reading and building.
  • A "done" is a claim. Wren re-runs the check before it believes a helper, and so should you.
  • Borrow openly, then add only what fixes a repeat failure. We borrowed openly from Hermes and OpenClaw: the persona, the lesson saved before each reset, the rules for what not to remember. After that, a new habit gets in only when it fixes a failure we keep hitting.
  • Remove scaffolding as models improve. Each new Claude model needs less hand-holding, so hooks and rules get re-tested and dropped once they stop paying.
  • Control the server, control the gates. You decide what runs, where, and what needs your yes first.
