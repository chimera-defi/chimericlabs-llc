How the SHA-256 miner got faster

The miner guesses text until the hash starts with letters we pick. In one short test, our change made it about 1.5 times faster. Three pictures first, then five short steps.

Read the limits first. This is one short test on one shared, busy computer. It is not a controlled benchmark. Expect no gain on chips with SHA-NI or AVX-512. We did not measure which part of the change explains the gain. The change is Proposed, not merged as spool-labs/sha256 pull request #4.

Is the prefix fixed at six letters? No. The miner takes 1 to 10 Base64 characters, or 1 to 16 hex characters (target()). “gensys” is only our example phrase. Our example prefix, “gensy”, has five characters.

Each extra Base64 character makes the search 64 times longer on average. The fast filter looks at up to 32 bits. The full check looks at the whole prefix. The ruler in step 4 shows both. To see how long your own prefix would take, use the search cost calculator.

Five steps, about 15 minutes

  1. The miner: a loop of guesses, hashed and checked against a prefix. 3 min.
  2. SHA-256: a 256-bit fingerprint, with no shortcut backwards. 2 min.
  3. AVX2: eight 32-bit lanes in one register. 3 min.
  4. What changed: keep 32 bits as a filter, re-hash the survivors. 4 min.
  5. The test: how much faster, and how far to trust it. 3 min.

Step 1 of 5 · 3 min

The miner is a loop of guesses

It makes a guess, hashes it, and checks the start of the result. It repeats until one matches. This finds a real hash that happens to start that way. It never edits a hash, and it is not Bitcoin mining.[1]

  1. GuessA phrase plus a counter: gensys:60237861.
  2. HashSHA-256 turns it into a 256-bit digest, a fingerprint of 32 bytes. It is a fixed recipe with no key. In hex it begins 81e9ecc9….
  3. SpellBase64 is a way to spell bytes with letters, digits, + and /. It uses 6 bits per character: gensyT8AF4HH….
  4. CompareDoes the text start with the prefix, the first characters we want, here gensy? Yes: stop and print it. No: add 1 to the counter and go back to 1.

Here are two real passes.

  • NOgensys:60237860 → CavohN5mTw51SHkP+fQpSRLWfJbB87B0razFJM55G3Y=. It starts with Cavoh, not gensy. The miner moves on.
  • YESgensys:60237861 → gensyT8AF4HHhEQvm/ieh0R05yWqjtlAd3ONa/xPjdk=. It starts with gensy. That is a hit, so the miner stops.

We worked both out with Python and with this command:

printf %s 'gensys:60237861' | openssl dgst -sha256 -binary | base64

With scripts on, this page recomputes them too. The hit took about 60 million guesses. Five exact characters need about a billion on average, so that was lucky.[2]

Try it: search yourself

Pick a phrase and a prefix of 1 to 3 characters. Letters, digits, + and / work, and case matters. Your browser hashes phrase:0, phrase:1 and so on until the Base64 text starts with your prefix. It stops after 1,000,000 guesses, or when you press Stop. The real miner takes up to 10 characters. Your browser stays at 3 so it can finish.

The live search needs JavaScript, which is off. The two real passes above are still correct.

Go deeper: work, proof and ignore-case

Each extra exact-case Base64 character makes the search 64 times longer on average. One character is 6 bits, and 26 = 64. A 2-character prefix needs about 4,096 guesses. A 3-character one needs about 262,144.

Luck varies. About 2 runs in 100 need more than 1,000,000 guesses for 3 characters. That is why the search above has a cap.

The real miner re-checks every hit with a separate reference SHA-256 before it prints it.[3]

The miner also has an ignore-case mode. Upper and lower case both match, so a letter is 1 in 32 instead of 1 in 64. Digits, + and / stay 1 in 64. The odds depend on which characters the prefix has. This page uses exact case. The prefix gensy is lowercase, so both modes accept the example.[4]

Step 2 of 5 · 2 min

SHA-256 gives no shortcut, so the miner guesses

SHA-256 turns any input into a 256-bit digest. A bit is a 0 or a 1, so that is 32 bytes.[5] Change one character of the input and about half the bits flip. They flip in no pattern you can work backwards. Nobody knows a way from “a digest that starts like this” to an input. So the miner can only try inputs.

Go deeper: why 140, and what “avalanche” means

If each bit flipped like a fair coin, you would expect 128 flips. 140 is an ordinary result for 256 tosses. Other one-character changes land near 128 too. “Half the bits change after a tiny change” is the avalanche effect.

A prefix of N bits is hit by about one guess in 2N. That is where the 64-fold rule in step 1 comes from. SHA-256 is a public standard, not something we wrote.

Step 3 of 5 · 3 min

One AVX2 register holds eight 32-bit words

So one instruction works on eight guesses at once. A processor keeps values in registers, small fast slots. An AVX2 register is 256 bits wide. SHA-256 uses 32-bit words, and 256 ÷ 32 = 8. Each 32-bit slice is a lane.[6] The lanes stay separate here. AVX2 can shuffle values between lanes, but this layout does not need that.

One at a time123456788 instructions
Eight lanes11 instruction

The same eight additions, counted both ways. The squares are instructions.

Here is one tiny step, in three parts.

  1. Put one guess in each lane, gensys:0 to gensys:7. SHA-256 reads 32-bit words. The second word of each guess is ys: plus the counter digit.
  2. Add the second SHA-256 round constant, 0x71374491, to every lane. One instruction does it: _mm256_add_epi32. One value at a time would take eight.
  3. That is one tiny step of one round. A whole hash keeps 8 working values and a message schedule for each guess. Each is its own register, with one lane per guess. So eight lanes hold eight words of eight guesses. They are not eight finished hashes.

Why one register is not one hash

Schematic This is not the real instruction sequence. Each row is one register. Each square is one guess’s value in it.

a01234567 b01234567 c01234567 d01234567 e01234567 f01234567 g01234567 h01234567 w…01234567

Rows a to h are SHA-256’s eight working values. w… stands for the message words it mixes in. A hash repeats many such steps, for all eight guesses together. Some steps cannot be spread across lanes. So eight lanes does not mean eight times faster, and this page makes no such claim. The library we started from already hashed eight guesses this way.[7]

Go deeper: AVX-512 and SHA-NI

Some processors have wider AVX-512 registers, with 16 lanes. Some have dedicated SHA instructions, called SHA-NI. The library checks the processor at start-up and picks the first of these that fits:

  1. AVX-512. AMD Zen 4 chips with SHA-NI skip this and fall through. Zen 5 uses a double-width variant.
  2. SHA-NI.
  3. AVX2, eight lanes.
  4. Plain portable code.

Our change targets the AVX2 choice. It applies to a processor with AVX2 and neither SHA-NI nor AVX-512.[8] The Intel Intrinsics Guide lists every AVX2 instruction.

Step 4 of 5 · 4 min

We changed the end of the hash call

The library already hashed eight guesses at a time with AVX2. We did not add that, and the 64 rounds are the same. What differs is what comes out. A miner only needs the start of each digest. So our call returns the first 32 bits of each one, not all 32 bytes.[9]

Those 32 bits are a filter: a cheap test that throws out almost every guess. A guess that passes is re-hashed the slow, safe way. Then the whole prefix is checked. So a filter pass is never reported as a hit. In the miner, one line does both: the filter, then the full check. Here are the two key spots, copied from the Rust source (exact-case branch):

// head_filter(), lines 147, 149 and 150: keep at most the top 32 bits
let m = bits.min(32);
let mask = u32::MAX << (32 - m);
let expected = ((exact_target >> (bits - m)) as u32) << (32 - m);

// mine_range(), lines 324 to 325: the filter first, then the full check
if head & mask == expected && sp.matches(n + i as u64).is_some() {
    return ChunkResult::Found(n + i as u64);
}

How wide is the filter?

It compares the top min(prefix bits, 32) bits of the first word.[10] A Base64 character is 6 bits, so a prefix of N characters is 6N bits. Short prefixes fit inside the filter. Long ones need the full check for the rest.

“Guesses on average” is 2bits, worked out from the prefix size. It is not a measured figure.

Hex prefixes work the same way. A hex character is 4 bits, so each extra one makes the search 16 times longer. The miner takes 1 to 16 of them, in lowercase, and the filter stops at 8. Ignore-case works for Base64 only.[15] In ignore-case mode the filter treats upper and lower case as equal, again over the first 32 bits. Survivors are still checked in full.

When the new path runs. Only when the library picked its AVX2 kernel. The whole message, phrase plus colon plus counter, must also fit one 64-byte block. That means 55 bytes at most: 64, minus 1 padding byte and 8 length bytes. Anywhere else the stock path runs, and the answers are identical.[11]

What we know and what we don’t. From the design and the source: same rounds, a first-word output, the filter, and a full re-check of survivors. Measured once, in step 5: about 1.5 times faster. Not established: how much of that each piece explains. Nobody profiled the run.

Proposed, not merged We proposed the change to the library as spool-labs/sha256 pull request #4. Until it is merged and released, the miner builds against a fork that carries it.

Read the code: target() turns the prefix into bits. head_filter() builds the 32-bit mask. prefix_matches() is the full check.

Go deeper: the hand-written kernel that lost

The miner also has an opt-in 8-lane kernel of its own. In every comparison we have, the patched library’s median or mean was higher. These are different comparisons on the same shared computer. None is part of the 1.52 figure. They are in the table of other runs in step 5.[12]

What this is not.

It is three pairs on one shared Intel i7-8700, which has AVX2 and no SHA-NI. The computer got busier during the run. The 1-minute load rose from 2.3 to 5.7. The clock was not locked. Part of the first pair’s 1.33 is noise. “Stock” still includes the miner’s own running counter, so it is not untouched library code.

It is a short test, not a sustained run, and not a result for other processors. Where the library picks SHA-NI or AVX-512, the stock path runs, so expect no gain. We know what the change removes. We did not profile the run, so this page does not say how much each part explains.
