How the SHA-256 miner got faster

A miner here is a program that guesses. The library it started from already hashed eight guesses at once. Our change is a short filter that throws out nearly every guess cheaply, then fully checks the few that pass. Three pictures first, then the same story step by step.

Step by step

New words are explained where they first appear and listed in the word list.

  1. What does the miner do? A loop of guesses, hashed and checked against a prefix.
  2. What does SHA-256 do? A 256-bit fingerprint where one changed letter flips about half the bits.
  3. What does AVX2 do? Eight 32-bit lanes in one register.
  4. What changed? Keep only 32 bits per guess as a filter; re-hash survivors in full.
  5. How much faster, and how far can I trust that? The measured pilot.

1. What the miner does

What is this program actually doing?

It is a loop. Make a guess: a phrase plus a counter, like gensys:60237861. Hash it with SHA-256, which scrambles any text into a fixed-size digest (the fingerprint). Write the digest as text using Base64, a way to spell bytes with letters, digits, + and /. Check whether that text begins with the prefix we want, here gensy. If not, add one to the counter and go again. This finds a real hash that happens to start that way. It never edits a hash, and it is not Bitcoin mining.[1]

  • NOgensys:60237860 → digest as Base64: CavohN5mTw51SHkP+fQpSRLWfJbB87B0razFJM55G3Y=. It starts with Cavoh, not gensy, so the miner moves on.
  • YESgensys:60237861 → digest as Base64: gensyT8AF4HHhEQvm/ieh0R05yWqjtlAd3ONa/xPjdk=. It starts with gensy: a hit, so the miner stops and prints it.

Both rows are real. They were worked out independently with Python (hashlib and base64) and with the command printf %s 'gensys:60237861' | openssl dgst -sha256 -binary | base64. If your browser can run scripts, this page also recomputes them right now and says so under each row. That hit took about 60 million guesses; five exact characters need about a billion on average, so it was a lucky one.[2]

Follow one guess

  1. The guess is plain text: gensys:60237861. The phrase is fixed; the counter goes up by one each time.
  2. SHA-256 turns the text into a 256-bit digest (32 bytes). It is a fixed recipe with no key and no secret. In hex it begins 81e9ecc9….
  3. Base64 writes those bytes as text, 6 bits per character, so the digest becomes gensyT8AF4HH….
  4. Compare the first characters with the prefix gensy. They match, so this is a hit. For …60237860 they do not, and the loop continues.

Try it: search yourself

Pick a phrase and a short prefix (1 to 3 characters; letters, digits, + or /; case matters). Your browser then hashes phrase:0, phrase:1, … until the Base64 text starts with the prefix. It stops after 1,000,000 guesses, or when you press Stop.

The live search needs JavaScript, which is off. The two real rows above are still correct.

Go deeper: work, proof and ignore-case

Each extra exact-case Base64 character makes the search 64 times longer on average, because one character is 6 bits and 2^6 = 64. A 2-character prefix needs about 4,096 guesses, a 3-character one about 262,144. Luck varies: about 2 runs in 100 need more than 1,000,000 guesses for a 3-character prefix, which is why the search above has a cap.

Every hit the real miner reports is re-checked with a separate reference SHA-256 before it is printed.[3] The miner also has an optional ignore-case mode, where uppercase and lowercase letters both count as matches, so each letter in the prefix is 1 in 32 instead of 1 in 64; digits, + and / stay 1 in 64. The odds depend on which characters the prefix has. This page uses the default, exact-case.[4] The prefix gensy is lowercase, so both modes accept this example.

2. What SHA-256 does to a guess

Why must the miner guess at all?

SHA-256 gives every input a 256-bit digest. A bit is a 0 or a 1, so the digest is 256 of them, the same as 32 bytes.[5] Change one character of the input and about half of those bits flip, in no pattern anyone can work backwards. Nobody knows a shortcut from “I want a digest that starts like this” to an input that produces it, so the miner can only try inputs.

Go deeper: why 140, and what “avalanche” means

If each bit flipped by a fair coin toss, you would expect 128 flips. 140 is an ordinary outcome for 256 tosses; other single-character changes give other counts near 128. That “half the bits change after a tiny change” behaviour is called the avalanche effect. SHA-256 itself is a public standard, not something we wrote.

A prefix of N bits is hit by about one guess in 2^N, which is where the 64-fold rule in section 1 comes from.

3. What “eight lanes” means

What does an AVX2 register actually hold?

A processor works on values held in registers, small fast slots inside it. An AVX2 register is 256 bits wide. SHA-256 works on 32-bit words, and 256 ÷ 32 = 8, so one register holds eight words side by side. Each of the eight 32-bit slices is a lane. One AVX2 instruction acts on all eight lanes at once. The instructions used here keep each lane separate; AVX2 does have shuffle instructions that move values between lanes, but this hashing layout does not need them.[6]

The eight lanes are the first picture on this page: one colour and number per guess, the same in every picture below. A row of eight is a whole register; one coloured square is one 32-bit value.

One instruction, eight guesses

  1. Put one guess in each lane: here guesses gensys:0 to gensys:7. SHA-256 reads a message as 32-bit words; the second word of each is the four characters ys: plus the counter digit.
  2. Add the second SHA-256 round constant 0x71374491 to every lane with a single instruction (_mm256_add_epi32). The table below uses real values, and this page recomputes them. Doing it one value at a time takes eight instructions.
  3. That is only one tiny step of one round. A whole hash keeps 8 working values plus a message schedule for each guess, so in a layout like this each of those is its own register, with one lane per guess. Eight lanes are eight words of eight different guesses, not eight finished hashes in one register.

Rows a to h are SHA-256's eight working values; w… stands for the message words it mixes in. The 64 rounds of a hash then repeat many such steps, for all eight guesses together. Some steps cannot be spread across lanes, so eight lanes does not mean eight times faster, and this page makes no such claim. The library we start from already hashed eight guesses at once this way.[7]

Go deeper: AVX-512 and SHA-NI

Some processors have wider AVX-512 registers (16 lanes) or dedicated SHA instructions, called SHA-NI. The library checks the processor when the program starts and picks, in this order: AVX-512 if available (AMD Zen 4 chips with SHA-NI fall through to the next choice; Zen 5 uses a double-width variant), then SHA-NI, then AVX2 with eight lanes, then plain portable code. The change in the next section targets the AVX2 choice, so it applies to a processor with AVX2 and neither SHA-NI nor AVX-512.[8] The Intel Intrinsics Guide lists every AVX2 instruction.

4. What we changed

What exactly is different from the library we started with?

The library already hashed eight guesses at a time with AVX2: we did not add that. The 64 rounds of SHA-256 are the same. What differs is the end. A miner only needs the start of each digest, so our call hands back just the first 32 bits of each one instead of writing out all 32 bytes.[9] Those 32 bits are only a filter: a quick, cheap test that throws out almost every guess. A guess that passes is re-hashed the slow, safe way and checked against the whole prefix, so a filter pass is never reported as a hit.

How wide is the filter?

The filter compares the top min(prefix bits, 32) bits of the first word. A prefix of N Base64 characters is 6N bits.[10]

In ignore-case mode the filter treats upper and lower case letters as equal, again over the first 32 bits only; survivors are still checked in full.

When the new path runs. Only when the library picked its AVX2 kernel, and only if the whole message (phrase, colon and counter) fits in one 64-byte hashing block: at most 55 bytes (64, minus 1 padding byte and 8 length bytes). Anywhere else the stock path runs and the answers are identical.[11]

Known and not known. Known from the design and source: the same rounds, a first-word output, the filter, and the full re-check of survivors. Measured, once, in the next section: about 1.5 times faster. Not established: how much of that each piece explains, because nobody profiled the run.

Proposed, not merged The change is proposed to the library as spool-labs/sha256 pull request #4. Until it is merged and released, the miner builds against a fork that carries it.

Go deeper: the hand-written kernel that lost

The miner also has an opt-in 8-lane kernel of its own. In every comparison we have, the patched library's median or mean was higher. Those are different comparisons on the same shared computer, and none is part of the 1.52 figure; they are in the table of other runs in section 5.[12]

What this is not.

Three pairs on one shared Intel i7-8700 (AVX2, no SHA-NI) that got busier during the run: the 1-minute load rose from 2.3 to 5.7. The clock was not locked, and the first pair's 1.33 is partly noise. “Stock” still includes the miner's own running counter, so it is not untouched library code.

It is a short pilot, not a sustained run, and not a result for other processors. Where the library picks SHA-NI or AVX-512, the stock path runs and you should expect no gain. We know what the change removes, but we did not profile the run, so this page does not say how much of the gain each part explains.
