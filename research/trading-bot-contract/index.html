What the trading bot contract 0x51C7…2A7F does

It is a privately run trading and market-making bot that is also its own wallet. We read its verified source, rebuilt it, and checked the build against the chain.

0x51C72848c68a965f66FA7a88855F9f7784502a7F on Etherscan

What it does

It trades its own funds on Uniswap and Curve, confirms its signed quotes for 0x and AirSwap orders, and pays out to an approved list of addresses.

Who it is for

Only the people who run it. It has no deposit function and no user balances. Outsiders have no reason to call it.

What to watch for

Anything sent to it by mistake can't be pulled back by the sender. An unknown function call succeeds and does nothing. A registry contract decides who can move its funds.

In plain words

Operatorsswap on whitelisted pools and can tip the block builder
RFQ signeran off-chain key whose signed quotes the bot vouches for
Transfererssend tokens or ETH, only to approved recipients
A registry contract sets every list. A multisig owns the bot and approves token allowances.

The verified source calls itself an “MEV bot and contract wallet”. MEV bots trade on price gaps between pools inside a single block. This one also acts as a market maker: when 0x or AirSwap settle an order against it, they ask the bot whether the quote was really signed by its key.

Verdict: it is not a drainer and not a honeypot. No function lets an outsider take funds, and no function pulls tokens from anyone. Every path that moves value needs a role, a whitelist or an allowance.

What a reviewer would flag

These are design facts, not claims that anything has gone wrong.

  • The registry holds the keys. It names the transferers and the recipients, and those two lists together are enough to send out any token or ETH. The registry contract is not verified on Sourcify or Blockscout, so its own rules can't be read.
  • The Curve payment trusts the transaction's sender. It checks tx.origin and the pool list, not whether the bot started the swap. Curve pools join the list without a factory check (lines 285–287).
  • A failed revoke drops the token anyway. The token leaves the tracked list before its approve(0) runs. If that call fails, a log is the only trace (lines 416–426).
  • Some results are ignored: ETH payouts (line 489), builder tips (686) and pool payments (589, 656, 665, 669, 678).
  • A stored timelock is never enforced here. timelockDelay is set once and only read back (lines 128, 176, 362).
  • No upgrade path. There is no proxy, delegatecall or selfdestruct. The owner, registry and WETH addresses are fixed at deploy.

State read on 14 Nov 2026 (block 26,415,084): the bot is on. It has 10 approved spenders, among them Uniswap's Permit2 and 1inch's router, and 161 approved tokens with 613 open allowances.

What we checked, and what we didn't

Checked

  • The verified source, built with the exact compiler and settings, gives the deployed code byte for byte, deploy arguments included.
  • We wrote a shorter readable version. It has the same functions, argument types and storage layout.
  • Run side by side from the same address, the deployed bytes and the readable version gave identical results on every step of a test that calls every external function.
  • On a local copy of mainnet at block 26,415,084, both gave the same output for a real swap and zeroed the same 613 allowances.

Not checked

  • The metadata hash differs, as it must: the verified file is a reconstruction with stand-in names, listed as a partial match on Sourcify.
  • Equivalence for every possible input. Tests are examples, not a proof.
  • The outside contracts: the registry, the multisig's signers, the venues and the spenders.
  • Who runs it. We make no claim about that.

How to read a contract on Etherscan

Open the address and pick the Contract tab. A green check means the source is verified: it was compiled and matched to the code on chain. Code shows the source, and Read Contract shows its current state without sending anything. Leave Write Contract alone: it asks your wallet to sign a transaction.
